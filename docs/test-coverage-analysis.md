# Анализ покрытия тестами

> Подготовлено Claude Code (облачная сессия на claude.ai/code) для проекта
> `telegram-claude-bridge`. Документ предназначен для передачи локальному агенту
> «Один» на чтение, обсуждение и, возможно, реализацию.

## Текущее состояние: 0%

Тестов нет вообще. Нет тестового фреймворка, CI, тестовых зависимостей.
Весь проект — это `webhook_server.py` (220 строк) плюс `setup_webhooks.sh` и
файлы конфигурации/сервисов. Один коммит, нет каталога `.github/`, нет
`pytest`/`tox`/`pyproject`.

Хорошая новость: код небольшой, логика хорошо изолирована — несколько тестов
дадут много уверенности. Сложность: почти всё имеет побочные эффекты (сеть,
`subprocess`, потоки, файловая система, HTTP-сервер), поэтому первая настоящая
работа — сделать код тестируемым, а не просто писать проверки.

## Где сосредоточен риск

Приоритеты примерно по принципу «что ломается в проде незаметно».

### 1. Загрузка конфигурации и маршрутизация ботов
`load_config` + парсинг на уровне модуля, строки 27–53 — *максимальная отдача,
проще всего тестировать.*

- `TOKEN_TO_AGENT` использует ключом `token.split(":")[0]` — числовой префикс
  токена. Если у двух ботов одинаковый префикс (или в токене нет `:`),
  маршрутизация молча ломается. Ничто это не защищает.
- `agent["name"]` и `agent["token"]` читаются без `.get()` — конфиг без любого
  из этих ключей роняет весь сервер уже на импорте. Нужен тест на внятную ошибку.
- Приоритет переопределений: переменные окружения (`WEBHOOK_PORT`, `CLAUDE_BIN`,
  `MAX_PARALLEL`) против значений из конфига против захардкоженных дефолтов —
  три уровня, которые ничто не проверяет.
- **Блокер:** логика выполняется при импорте модуля, поэтому без рефакторинга в
  функцию (например `build_bots(config)`) её не протестировать. Это самое
  полезное изменение для тестируемости.

### 2. Обработчик webhook-запросов
`WebhookHandler.do_POST`, строки 131–182 — *наиболее важен для безопасности.*

- **Авторизация:** фильтрация по `ALLOWED_CHATS` (строка 162). Регрессия здесь =
  кто угодно может управлять Claude CLI. Первое, что стоит зафиксировать тестом,
  включая поведение «пустое множество = разрешить всем».
- Неизвестный/невалидный префикс токена → всё равно вернуть 200, но не
  обрабатывать (строки 146–147).
- Некорректный JSON (строка 154), отсутствие `message`, фоллбэк на
  `edited_message`, пустой `text` с фоллбэком на `caption` (строки 157–167).
- Контракт «всегда сразу отвечать 200» — Telegram повторяет запрос при не-200.

### 3. Обработка сообщений
`process_message`, строки 82–122.

- Успех `subprocess`, **таймаут** (строка 108), общее исключение (строка 110) →
  каждый маппится в конкретную строку для пользователя. Легко мокается.
- Пустой stdout → фоллбэк `"Could not process. Try again."` (строка 107).
- **Разбивка по 4000 символов** (строка 118) — классические ошибки на границах.
  Тесты на 4000, 4001, пустую строку, несколько частей. Скрытый баг: пустой
  ответ даёт ноль частей → ничего не отправляется.
- Поток typing-индикатора и семафор: как минимум проверить, что `stop_typing`
  устанавливается в `finally`.

### 4. Сохранение истории
`save_history`, строки 66–70.

- Формат JSONL, дозапись, `ensure_ascii=False` (юникод), имя файла из имени
  агента. Тривиально через `tmp_path`. Заодно проверить, что странное значение
  `agent` не выходит за пределы каталога истории (path-traversal).

### 5. `setup_webhooks.sh` / `tg_call`
Ниже приоритет. `tg_call` глотает все исключения (строка 78) → сбои невидимы;
тест мог бы хотя бы зафиксировать построение URL и кодирование.

## Конкретные рекомендации

1. **Сначала инфраструктура:** `pytest`, каталог `tests/`, workflow в GitHub
   Actions с `pytest --cov`. Можно подключить скилл `session-start-hook` для
   запуска тестов/линтеров в веб-сессиях.
2. **Рефакторинг для тестируемости:** вынести парсинг конфига/ботов с уровня
   модуля в чистые функции; вытащить разбор тела из `do_POST` в функцию
   `(update_dict, agent) -> action`. Тогда маршрутизацию/авторизацию/парсинг
   можно тестировать без `HTTPServer` и моков `rfile`/`wfile`.
3. **Мокать границы:** `subprocess.run`, `urllib.request.urlopen`, `tmp_path`
   для истории. Никакой реальной сети и CLI в тестах.
4. **Пара интеграционных тестов:** `HTTPServer` на порту 0 в потоке, реальный
   Telegram-payload, проверка 200 + что замоканный вызов Claude сработал.
5. **Отдельно покрыть ветку безопасности:** проверка `ALLOWED_CHATS` —
   выделенный тест с комментарием про подводный камень «пусто = разрешить всем».

Сфокусированный набор из ~20–25 тестов поднимет покрытие с 0% до осмысленного по
каждой важной ветке.
